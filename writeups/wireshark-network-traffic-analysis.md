# Wireshark Lab: Reading My Own Network Traffic

**Part of my 90-day cybersecurity challenge** | Week 4 (27 Oct - 2 Nov 2026) | Lane: Blue team / DFIR

After a week of studying networking theory (the OSI model, devices, IP, ports, DNS, logs and monitoring), I captured my own traffic in Wireshark to see those ideas as real packets. I followed one website, `example.com`, from the DNS lookup, through a ping and a TCP handshake, to a plaintext HTTP page and an encrypted HTTPS connection, and compared what an observer can and cannot see in each case.

## 1. Objective and scope

**Objective:** see, in real packets, the concepts from this week's study: OSI layers, DNS resolution, ICMP, the TCP three-way handshake, and the difference between HTTP and HTTPS.

**Scope and ethics:**
- I captured only traffic generated by my own virtual machine on my own connection.
- The target, `example.com`, is a domain reserved for documentation and testing examples.
- I have not published any capture files. Only screenshots are included here.

## 3. Method

I generated traffic from a second terminal while Wireshark was capturing:

```
ping -c 4 example.com
curl http://example.com
curl -I https://example.com
```

Then I stopped each capture and used display filters to isolate each protocol:

| Filter | Purpose |
|--------|---------|
| `dns` | Name lookups |
| `icmp` | The ping |
| `tcp.port == 80` | The TCP handshake and plaintext HTTP |
| `http` + Follow TCP Stream | Rebuild the HTTP conversation as readable text |
| `tls` | The encrypted HTTPS connection |

## 4. Findings

### 4.1 DNS: turning a name into an address

![DNS queries and responses](images/01-dns-query-response.png)

- Every **query** from my VM (`10.0.2.15`) to the DNS server (`10.0.2.3`) had a matching **response**, usually about 70 ms later.
- The queries travel over **UDP**, and the DNS server listens on **port 53**.
- The VM asked for an **A** record (IPv4) and an **AAAA** record (IPv6) within a millisecond of each other, which is normal behavior. A reverse lookup (**PTR** query) also appeared.
- The responses carried the flags `0x8180`: a standard response, recursion available, no error. Each had 1 question and 2 answers.

![DNS answer bytes](images/02-dns-answers-hex.png)

The answers for `example.com`:

| Type | Address | TTL |
|------|---------|-----|
| A | `104.20.23.154` | 300 s |
| A | `172.66.147.243` | 300 s |
| AAAA | `2606:4700:10::ac42:93f3` | 300 s |
| AAAA | `2606:4700:10::6814:179a` | 300 s |

The TTL appears in the raw bytes as `00 00 01 2c`, which is 300 in hex: a resolver may cache this answer for 5 minutes. I also decoded an address by hand from the bytes: `68 14 17 9a` is 104.20.23.154. The addresses belong to Cloudflare, which sits in front of the site.

### 4.2 ICMP: the ping

![ICMP echo requests and replies](images/03-icmp-ping.png)

- 4 echo **requests** and 4 echo **replies**, 8 packets in total.
- The destination was `104.20.23.154`, **the same address DNS returned**. So the chain is: DNS resolves the name, then the next tool uses the address.
- Round-trip time was about **65 to 68 ms** for each pair.
- ICMP has **no ports** and no TCP or UDP layer. It sits directly on IP. The request is ICMP **type 8** (echo request), the IP protocol number is 1, and the IP **TTL** (hop limit) is 64. This is separate from the DNS TTL.

### 4.3 TCP: the three-way handshake

![TCP handshake and HTTP request](images/04-tcp-handshake.png)

| Packet | Event |
|--------|-------|
| 29 | **SYN**: my VM (port 59182) asks to connect to `104.20.23.154` port 80 |
| 30 | **SYN, ACK**: the server agrees (about 68 ms later) |
| 31 | **ACK**: connection established |
| 32 | **HTTP `GET / HTTP/1.1`** |
| 34 | **HTTP/1.1 200 OK** |
| 35 to 39 | **FIN, ACK** from each side and a final ACK: a polite close |

Observations:
- Source port **59182** comes from the dynamic range (49152 to 65535). The destination, **80**, is the well-known HTTP port.
- The first two packets in the filtered list (27 and 28) were an attempt to connect over **IPv6**. The server side answered with a **[RST, ACK]**, meaning the connection was refused, and `curl` then retried over IPv4 and succeeded. The likely cause is that my VM's NAT network does not route IPv6, but I did not confirm that.
- The sizes add up: my request used 75 bytes of HTTP text and the server's reply 936 bytes, matching the 1,011 bytes of application data Wireshark reported for the stream.

### 4.4 HTTP: everything is readable

![HTTP conversation in plaintext](images/05-http-plaintext-stream.png)

Using **Follow TCP Stream**, Wireshark rebuilt the full conversation.

**My request (client to server):**
- `GET / HTTP/1.1`
- `Host: example.com`
- `User-Agent: curl/8.22.0`
- `Accept: */*`

**The server's response:**
- `HTTP/1.1 200 OK`, `Content-Type: text/html`
- `Server: cloudflare`
- `cf-cache-status: HIT` and `Age: 8063`: Cloudflare served a cached copy about 2 hours 14 minutes old, so my request never reached the origin server
- `Transfer-Encoding: chunked`
- `alt-svc: h3=":443"`: the server advertises HTTP/3 on port 443
- The full HTML page

Anyone who could see this traffic could read the site visited, the program making the request, and the entire page.

### 4.5 HTTPS: the same site, encrypted

![TLS handshake and encrypted application data](images/06-tls-encrypted-traffic.png)

In the second capture, Wireshark labels the connection **TLSv1.3**:

- **Client Hello** (1,749 bytes): my VM opens the conversation and says which encryption it supports.
- **Server Hello, Change Cipher Spec** (2,934 bytes): the server picks the settings and both sides move to encrypted communication.
- Everything after that is **Application Data**. In the raw bytes, the text column is random symbols with nothing readable.

![TLS Client Hello details](images/07-tls-client-hello.png)

The Client Hello shows a few important things:
- The record version says TLS 1.0 and the handshake says TLS 1.2, even though the connection is TLS 1.3. This is deliberate: TLS 1.3 fills those older fields for compatibility, and the real version is negotiated in an extension. Misreading this could lead an analyst to report a weak protocol that is not actually in use.
- The **server name (SNI)**, `example.com`, is sent unencrypted so the server knows which certificate to present.

### 4.6 Side by side

| | HTTP (port 80) | HTTPS (port 443) |
|---|---|---|
| Request and page contents | **Readable** | **Encrypted** |
| IP addresses and ports | Visible | Visible |
| Packet sizes and timing | Visible | Visible |
| Site name | Visible (`Host:` header) | Visible (SNI in the Client Hello) |

## 5. Mapping to the OSI model

Expanding any packet in Wireshark shows the layers stacked, matching the model I studied:

| OSI layer | What I saw |
|-----------|-----------|
| 7 Application | DNS, HTTP |
| 6 Presentation | TLS encryption |
| 4 Transport | UDP (DNS) and TCP (HTTP, HTTPS) with ports |
| 3 Network | IPv4 and IPv6 addresses, ICMP |
| 2 Data link | Ethernet II with MAC addresses (my VM's starts with `08:00:27`, the VirtualBox vendor prefix) |
| 1 Physical | Represented by the captured frame |

## 6. Security analysis

1. **Plaintext protocols expose everything.** One readable HTTP stream gave away the site, the client software and the full page. If it had carried a password or session cookie, the observer would have had that too.
2. **HTTPS hides contents but not metadata.** IP addresses, ports, packet sizes, timing and the site name (SNI) stay visible. For a defender that is still valuable evidence.
3. **DNS shows intent.** The names a machine looks up can reveal what it is about to contact, which is why DNS logs help detect malware reaching out to its controller. Encrypted DNS (DoT on TCP 853, DoH on TCP 443) would hide this from network monitoring.
4. **Details in headers become indicators.** User-Agent strings, server banners and cache headers help analysts spot unusual clients or identify infrastructure.
5. **Refused connections leave a pattern.** The failed IPv6 attempt produced a RST. A host making many connections that get refused is the kind of pattern that shows up in firewall logs and can indicate scanning.
6. **Read the whole header before judging.** The TLS version fields looked like an outdated protocol but were a compatibility feature.

---

## 7. Limitations

- Small lab capture to a single destination; real networks are noisier.
- VirtualBox NAT hides the real network topology, and my explanation for the IPv6 refusal is unconfirmed.
- I did not decrypt the TLS traffic, so I only observed what stays visible.
- I captured everything on the interface without capture filters, which is fine in a lab but would be too much data on a busy network.
